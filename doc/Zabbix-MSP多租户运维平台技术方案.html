01

结论与需求边界

建议采用“独立 MSP 控制层 + Zabbix 监控资源池 + 客户侧 Proxy”的组合。通过 Zabbix API、模板、Webhook 和扩展接口完成主要集成；客户门户独立开发。标准客户共享受控监控实例，需要更强故障边界、独立保留策略或部署位置的客户使用独享实例。

核心判断 01

租户模型在平台层建立

主机组负责监控对象授权，平台补齐租户身份、对象归属、配额、审计与运营数据。标签只辅助路由与检索。

核心判断 02

采集与业务编排分开

Agent / Proxy 采集指标；API 管理配置、按需读取数据。平台持久化业务事件与处理状态，避免全量指标反复搬运。

核心判断 03

按监控实例扩展吞吐

Server 原生 HA 每次只有一个活动节点。增加 Proxy 扩展采集能力；超过单实例瓶颈后，再新增 Server 与数据库资源池。[05]

输入范围

截图明确要求：Zabbix 二次开发、API 后端、多租户隔离、告警渠道、可视化、CMDB / 工单 / Ansible 对接，以及大规模监控优化。本报告以截图中可见的岗位职责为需求线索。底部任职要求未完整展示，未推断公司现有技术栈、业务规模或预算。

03

总体架构与数据流

控制层负责“谁可以操作什么、请求如何闭环”；监控资源池负责“如何采集、计算、存储与产生事件”。每个资源池包含一套 Zabbix 实例及其数据库，可承载多个标准租户，也可独享给单个客户。

配置流

门户 → 业务事务 → Worker → API

保存期望配置与版本，同时写入 Outbox。Worker 根据租户路由调用对应 Zabbix API，记录实际结果，再定期检查配置漂移。前端展示“同步中 / 生效 / 失败”，而非提前宣布创建成功。

事件流

Zabbix → Webhook → 事件中心 → 闭环

事件先可靠落库，再返回成功并异步处理。事件中心去重、补齐资产上下文、分派通知与工单；恢复后复核执行结果并更新报告。

指标流

设备 → Agent / Proxy → Zabbix DB

指标查询先校验资产和 Item 所属，再按需读取历史或趋势。报表以业务聚合和小时趋势为主，避免控制层成为第二套全量时序存储。

资产流

CMDB → 平台映射 → Zabbix Host

CMDB 管理生命周期、负责人和服务关系；Zabbix 反馈监控状态与采集发现。IP 可能重复，不能用 IP 作为跨客户资产唯一键。

04

多租户建模与隔离

租户标识必须由可信登录上下文解析，并对每个对象实施授权。请求中的 tenant_id、主机名、标签和前端筛选都不能单独作为授权依据。跨客户值班人员通过受审计的“当前租户切换”工作；平台管理员的跨租户能力单独授权。

模式边界主要代价触发条件
共享监控实例独立主机组、受限身份、平台对象授权；共享 Server 与监控 DB存在共同故障域和资源争用；管理员可接触多个租户数据标准客户、监控配置及数据保留政策相近
独享监控实例独立 Server、DB、Proxy 路由和凭据；统一控制门户更多资源、备份和升级单元较高负载、独立数据留存 / 地域 / 变更窗口
独立部署控制层及监控层均在客户环境版本分散、远程维护与分发成本高客户要求自主管理全部系统，或网络无法接入共享控制层

六层约束

  1. 身份层：成员表 tenant_membership 保存用户、租户、角色与资源范围。每次切换校验成员关系，短期会话缓存授权版本，撤权后立即失效。
  2. 对象层：Host / Item / Trigger / Event / Dashboard / Report / Job 等所有入口都先验证 (tenant_id, object_id)。批量请求逐项授权；对象不存在与无权限统一响应，避免暴露客户资源。
  3. Zabbix 层：主机组按 tenant/{uuid}/{site} 分配，技术主机名带不可冲突标识；共享基础模板只允许平台发布。标准租户配受限的查询和配置身份；需更高权限的操作只在内部 Provisioner 中执行，不向门户提供任意 API 透传。
  4. 数据库层：平台业务表包含非空 tenant_id，复合外键与唯一键携带租户。启用 RLS 作为补充，应用连接使用非 owner、非 superuser、无 BYPASSRLS 的角色；每事务设置租户上下文，并防止连接池复用残留。[12]
  5. 缓存与任务层：缓存键包含租户、监控实例、权限版本和查询条件；消息写入可信租户与对象引用，消费时再次校验。报告下载使用授权后签发的短时地址，不能依赖路径不可猜测。
  6. 网络与执行层：Proxy、通知连接器和执行器按客户网络分配凭据；Worker 配置租户并发上限。任意 URL、任意脚本和任意主机清单均不作为面向客户的通用输入。
必须验证的 Zabbix 权限细节

不同用户组的 Read / Read-write 可能扩大访问，显式 Deny 会阻断访问；问题标签过滤控制的是问题可见性。不要把全局“Linux”“数据库”主机组赋给所有租户。所有新增主机组、成员变化和模板发布都要跑双租户回归。上述规则来自官方权限文档，完整 SaaS 隔离由本方案额外实现。[03]

写入失败和超时如何收敛

数据库事务只覆盖平台记录与 Outbox，不跨 Zabbix / ITSM 做分布式事务。对写请求使用 tenant_id + Idempotency-Key 唯一约束，并校验请求摘要；同一幂等键不同请求体返回冲突。调用超时视为“结果未知”，先按稳定技术名称 / 映射回读，再决定重试，避免重复创建。

Worker 按对象串行应用递增配置版本；失败进入可重试 / 需人工介入状态。对账检查“期望版本、已应用版本、实际配置摘要”。统一处理 HTTP 失败和 JSON-RPC 的 error 字段；对每个实例设置速率、并发和熔断，批量接口限制对象数。

示例起始限制：普通列表每页 100、最大 500；单图最多 20 条曲线、每条 1,000 个点；超过范围转异步报表或缩小时间窗。以上均为待压测的产品限制，不是 Zabbix 原生固定上限。

Proxy Group 的实际边界

它按主机重新分配实现采集故障转移，不能据此宣称按 NVPS 精确均衡，也不会消除单 Server 的处理瓶颈。组内 Proxy 必须能到达接管的全部目标；外部脚本与 ODBC 配置应一致，Agent / Proxy / Server 版本组合按文档验证。7.0 文档明确指出 Proxy Group 不支持 SNMP traps。[08]

网络原则：客户侧主动 Proxy 经 TLS 连接监控端点；Agent 主动检查连接被分配的 Proxy（通常 TCP 10051），被动检查按需开放目标 Agent 端口（通常 TCP 10050）。SNMP 轮询常用 UDP 161，Trap 常用 UDP 162；实际端口以部署配置为准。密钥按客户 / 站点隔离。未知 Agent 自动注册先进入待认领区，经资产校验后接入。

07

告警、通知与工单闭环

采用 Webhook 快速推送 + API 增量补偿 + 未闭合事件定期对账。通知发送和工单创建都采用至少一次尝试，通过幂等键约束业务副作用；不承诺跨多个外部系统的端到端“恰好一次”。Zabbix Webhook 支持脚本发起 HTTP 请求，可连接平台事件入口。[09]

归并与降噪去重、依赖抑制、维护窗口、抖动控制

事件模型与可靠性规则

  • 事件幂等：原始事件主键为 (instance_id, eventid)；通知去重键加入渠道、接收对象及事件阶段。更新 / 确认消息可在同一 eventid 上出现，另存 update 标识或规范化内容摘要，不能全部按 eventid 丢弃。
  • 可信归属：Webhook 的租户标签只作线索，接收端根据已认证的 instance 与资产绑定推导租户。多主机 Trigger 必须限制在同一租户；未知或跨租户事件进入隔离队列，禁止自动派发。
  • 先持久化再确认：事件落库与 Outbox 同事务提交后返回成功；持久化失败返回失败，让发送端重试。消费失败指数退避，超过次数入死信；死信数量和最老年龄纳入平台自身监控。
  • 补偿读取：每实例保存 eventid 水位，使用 event.get 按 ID 升序和上限批量拉取，持久化整批后提交水位，边界重读去重。增加时间重叠窗口复扫，避免并发提交、短时故障等造成遗漏；最长中断不得超过源端事件保留期。[10]
  • 恢复对账：仅按新 eventid 拉取不能覆盖旧事件的确认 / 恢复字段变化，因此周期刷新所有未关闭事件及近期变更事件，并按 r_eventid 读取恢复关联。problem.get 主要用于未恢复及近期恢复问题，不能承担完整历史台账。[11]
  • 乱序处理：保留源事件时间与平台接收时间。恢复先到时创建待关联记录，之后补齐问题事件；重放历史消息不能把已恢复事件倒退为新问题。

平台视角

监控系统本身的健康

Proxy 延迟、Server 队列、DB 写入、API 延迟、Webhook 落库失败、补偿水位、死信与备份恢复状态。

Grafana 的文件夹和下拉变量不构成数据隔离

Grafana 默认允许组织内用户查询组织内数据源，细粒度数据源权限涉及 Enterprise / Cloud 能力。Direct DB 会绕过 Zabbix API 读取历史与趋势。因此客户门户默认由平台聚合 API 提供图表；若使用 Grafana，采用独立组织 / 实例和仅能访问该租户的受限数据源，并实际验证查询边界。共享全量监控数据库的 SQL 数据源只用于受控内部运营。[13][14]

SLA 与运营口径

服务可用性按服务树和事件区间计算，不能直接用“正常主机数 / 总主机数”替代。Zabbix 原生 SLA 支持服务关联、服务时段及排除停机；平台统一合同版本、时区、计划停机规则和月报快照。[16]

可用率 = 1 - 不可用时间并集 / 有效服务时间
有效服务时间 = 约定服务时段 - 经批准排除的时间区间
MTTA = 首次有效人工确认时间 - 问题发生时间
MTTR（本报告口径）= 监控恢复时间 - 问题发生时间
工单解决时长单独统计；无数据区间单列，不默认视为可用。

相同服务多个故障的重叠区间取并集，跨月事件裁剪到报表周期；同时报告均值、P95、样本量和未恢复数量。小时趋势用于容量展示，事件时间线用于可用性核算，不能用小时均值推断短时故障。

容量估算与性能策略

按有效 Item、更新频率、写入值数和查询负载测算，不能仅按主机数采购。一条主指标可能生成大量依赖指标；LLD、预处理、日志、事件和历史查询会增加开销。以下模型假设均匀周期采集，所有结果均为未压缩的粗估，不是已测吞吐。

可调整的容量模型 默认：5,000 台主机

12,500值 / 秒 · 平均 NVPS
86.40 GB每天历史数据 · 未压缩
2.59 TB历史数据总量 · 未压缩
672.77 GB趋势数据 · 按 128 字节 / 行
4.57 TB单节点估算 · 历史 + 趋势 + 余量
25,0002 倍峰值验证目标 · 值 / 秒

使用十进制单位：1 GB = 10⁹ 字节，1 TB = 10¹² 字节。80 字节 / 值与 128 字节 / 趋势行是包含索引等摊销的测算参数，需实测校准；不计压缩收益。运行余量不替代 WAL 峰值、数据库副本、备份、业务库、事件及日志的单独预算。

计算依据与默认结果

NVPS = 主机数 × 每台有效 Item ÷ 采样间隔
历史字节 = NVPS × 86,400 × 历史天数 × 每值字节
趋势字节 = 主机数 × Item × 数值项比例 × 24 × 趋势天数 × 128
单节点容量 =（历史字节 + 趋势字节）×（1 + 余量比例）

默认场景产生 75 万有效 Item、日均 10.8 亿个值。30 天历史约 2.592 TB，365 天趋势约 0.673 TB，合计加 40% 运行余量约 4.571 TB / 数据节点。主备各保留一份时约 9.141 TB，另加 WAL、备份及其他数据。计算器调整后，以实时输出为准；此段保留默认场景便于复核。

存储与保留政策

  • 分层保留：建议标准池历史 30 天、数值趋势 365 天；高频短期指标可缩短历史保留。需要更长原始数据的客户使用独享池或受控离线导出，避免拖累全池。
  • TimescaleDB：按官方脚本维护 hypertable 与 housekeeping；Zabbix 7.0 的相关配置存在全局历史 / 趋势保留覆盖，应将不同保留政策拆池。压缩窗口至少 7 天，且文档提示超过压缩窗口的迟到数据可能被丢弃；Proxy 离线期限与补传窗口必须一起验证。TimescaleDB 不用于 Proxy。[07]
  • 归档：平台审计、事件与月报按合同留存；原始指标如需归档，导出时保存 schema、租户 / 资产映射、时间范围与校验和。对象存储中的归档不会自动成为 Zabbix 在线历史，查询或恢复需单独流程。
  • Proxy 缓冲：按站点 NVPS × 最长断网秒数 × 实测每值空间 × 余量测量本地磁盘，并核查缓冲参数。Proxy Group 不代表本地待上送缓冲有同步副本，磁盘损坏后的数据损失边界需实测。

高可用、部署与平台运维

高可用必须分别覆盖入口、业务库、消息链路、监控 Server、监控数据库和客户采集网络。Zabbix 原生 Server HA 共享同一个数据库，每次只有一个活动节点；它不会顺带解决数据库可用性。[05]

门户 / API / Worker2 个以上无状态副本，跨故障域部署；任务消费幂等副本退出、发布中断、重复消费、缓存丢失
平台 PostgreSQL主备复制 + 独立备份 + 明确故障切换机制主库失败、网络分区、误删除、恢复后任务重放

故障目标 验收目标，待合同确认

首期试点以控制层可用性 99.9% 为候选目标（30 天约 43.2 分钟不可用预算），核心平台数据备份 RPO ≤ 15 分钟、灾难恢复 RTO ≤ 60 分钟；单组件主备切换另设较短目标并实测。Zabbix 故障转移时间取决于配置与外部数据库状态，不预先承诺“无损秒切”。

指标完整性按“预期采集值中成功入库比例”和端到端数据新鲜度分别衡量。断网时 Proxy 可缓冲，但缓存不足、介质损坏、超出保留或压缩补传窗口时不能保证指标 RPO 为零。每季度恢复演练覆盖业务库、Zabbix 配置、事件、证书与执行模板，不只检查备份文件存在。

部署起始配置与演进

PoC 示例为 200 台主机、每台 100 个 Item、60 秒间隔，平均约 333 NVPS。可从 API / Worker 各 4 vCPU / 8 GB、Zabbix Server 4 vCPU / 8 GB、监控 PostgreSQL 8 vCPU / 16 GB、Proxy 每台 2 vCPU / 4 GB 的测试资源起步；这是实验起点，不是 5,000 台生产环境的规格保证。用真实模板逐步放量，记录 CPU、内存、磁盘和查询并发，再确定生产节点。

数据库优先使用独立稳定存储；现有团队若擅长虚拟机与自动化配置，就以该方式运行监控核心。需要采用 Kubernetes 时，将数据库持久化、节点驱逐、Operator 升级及恢复责任纳入方案，不能把“容器有副本”视为数据库 HA。

升级、迁移与回退

  1. 固定基线：锁定 Zabbix / Proxy / Agent / DB / 扩展和模板版本；在预生产验证 API 契约、权限矩阵、典型触发器与升级脚本。
  2. 灰度升级：先选小型资源池，明确写入窗口与 Proxy 缓冲；比较升级前后采集延迟、事件数量和图表结果。按官方升级流程处理数据库及 TimescaleDB schema。
  3. 回退准备：升级前制作经验证的备份。数据库 schema 升级后，不能假设回滚容器镜像即可恢复；必要时恢复整个兼容版本数据库和配置，并对切换期间数据做补偿核查。
  4. 租户迁池：创建新池资源、保留平台资产 ID、校验新绑定与凭据；短暂双采时用迁移标记抑制重复通知，逐站切换并验证。旧历史保留只读路由到原池直至到期，避免高成本整库搬迁；回退使用原路由与时间化映射。

平台自身需要独立于被监控 Zabbix 的最小健康探测和告警渠道，以便在整个监控资源池不可用时仍能通知值班人员。

成本如何估，不给虚假的固定报价

5 人 × 14–16 周对应约 70–80 人周 的核心工作量；再为外部系统配合、现场差异及试点问题预留 20%–30%，预算量级约 84–104 人周。以上是范围估算，不是已批准排期；若要求大量设备模板、多个工单系统或客户私有部署，应拆分增量。

研发成本 ≈ 角色人周 × 各角色含税单价 + 外部集成费用
月运行成本 ≈ 各资源池计算 + 存储 / IOPS + 副本 / 备份 + 控制层 + 带宽 + 通知 + 值班与维护

资源报价应根据最终地域、供应商、压测规格和备份策略询价。开源组件不意味着运行与维护零成本；商业支持、通知套餐和数据源权限等如被选择，需单列费用。

下表是建设项目的验收建议，不代表本次调研已经完成平台开发或性能测试。性能用例采用确定的模板、数据分布和并发脚本，报告包含版本、环境、时间区间与原始数据。

验收项测试方式候选通过标准
跨租户隔离A / B 租户互换 hostid、itemid、eventid、报告、工单、任务及缓存键；覆盖批量、导出、撤权与异步消费全部越权请求被拒绝，零跨租户数据返回或执行；包含 Zabbix 受限凭据验证
配置一致性模拟 API 超时、重复请求、Worker 重启和人工配置漂移不重复创建资产；期望与实际可追踪，正常环境 5 分钟内收敛或显式报错
告警可靠性Webhook 重复 10 次、乱序、入口停机 30 分钟再恢复已知测试事件全部补齐，通知 / 工单副作用幂等，恢复关联正确；补偿在恢复后 5 分钟内完成
采集与 API 性能默认 12,500 NVPS 回放或等效生成，叠加 50 并发用户及典型报表稳定运行 24 小时，无持续积压；授权列表 API P95 ≤ 1 秒，仪表盘聚合 P95 ≤ 3 秒
峰值与过载2 倍写入峰值持续 30 分钟，叠加高成本租户查询核心事件不静默丢弃；系统限流或排队明确，恢复常态后 15 分钟内排空积压
通知时效记录问题生成、平台落库、请求渠道受理与回执时间正常负载从事件生成到渠道受理 P95 ≤ 30 秒；送达与用户响应分别报告
自动化执行跨租户目标、无审批、参数注入、重复执行、超时、目标失联无越权执行；审批可追溯；失败状态与目标实际状态可核对
HA / 恢复Server、数据库与 Proxy 故障注入；从备份恢复独立环境符合约定 RPO / RTO；清楚列出数据缺口、补传量和时间，禁止用进程启动代替恢复验证
SLA / 报表跨月、重叠故障、维护、时区、未知数据、未恢复事件样本与人工算例逐项一致，报告生成后具有口径版本与数据快照

建议首个评审里程碑
