# MOP平台开发文档

版本：V0.1；编制日期：2026年9月30日；用途：开发执行与客户规则确认。

[打开可搜索的本地阅读版](../../output/documents/MOP平台开发文档.html)。阅读版由本目录源文件生成，后续修订以可编辑源文件为准。

本套文档把合同、现有原型和上一版详细设计连接到可执行的开发任务。可以先做的工程基础、页面、接口契约和测试数据已单独划定；需要客户选择的业务规则、环境和集成方案保持待确认，不用建议值代替客户结论。

本轮完成的是开发设计和配套契约文件，尚未实现生产后端，也未完成真实设备或第三方联调。原型的演示交互不作为合同功能完成证明。本文件是后续开发入口，原合同及已输出文件保留原样。

## 配套文件

- `contracts/core-api.openapi.json`：首批可并行开发接口的OpenAPI 3.1设计契约，可导入兼容工具查看；不是已部署API。
- `contracts/config-baseline.json`：从确认清单提取的规则登记表。未确认项保持 `null`，不供应用直接当作运行配置使用。
- `evidence/contract_requirements.json`：从实际合同DOCX提取的128项功能原文，保留表格位置。
- `evidence/prototype_inventory.json`：原型页面盘点。
- `evidence/source_manifest.json`：本轮采用的本地资料及SHA-256，便于后续判断输入是否变化。
- `tools/build_docs.py`：检查链接、需求覆盖和核心契约，并生成本地HTML阅读版。它不部署应用、不连接客户系统。

## 本轮落地结果与下一步

开发从01中的D00至D04开始：资料基线、工程划分、页面组件、身份隔离接口、配置审批机制。随后先串联“租户与资产 → 事件 → 工单 → 客户确认 → 报告快照”的测试链路。数据库物理实现、生产组件集成、正式规则发布以及远程连接执行，分别等待对应结论。

待确认期间可以使用明确命名为 `fixture` 的本地假数据和适配器替身验证设计；不得把该模式暴露为客户生产服务。业务页面遇到未配置规则显示“规则待确认”并说明受影响动作；无数据显示“未知”或“—”，不能显示成功或达标。

## 后续维护方法

1. 修改章节源文件；客户确认只填写04并同步 `config-baseline.json`，保留版本和书面证据。
2. 修改核心API时同时编辑 `tools/build_core_contract.py` 并运行它，避免下次生成覆盖契约；后续全量接口另按03扩展。
3. 使用Python运行 `tools/build_docs.py` 做文档结构检查；脚本自动更新07追踪和来源清单。生成HTML时传入 `--node` 指定Node程序、`--packages` 指定含marked包的目录。本轮使用现有打包运行时，未向业务工程安装依赖。
4. 每次交付前检查生成的阅读版和客户空栏，再更新版本记录。脚本报告只证明静态文档检查，不是OpenAPI完整规范认证或产品功能测试。
