# 信锐 RS6300-50Q-EI-24X 开放接口与文档索引

> 调研时间：2026-10-12
> 结论一句话：**这台交换机没有面向二次开发的设备级 API（无 NETCONF / RESTCONF / RESTful / Telemetry），对外可编程能力只有 SNMP。**

---

## 一、先厘清品牌归属

| 项目 | 实际情况 |
|---|---|
| 你提供的型号 | 深信服 aRS6300-50Q-EI-24X |
| 官方型号 | **信锐 RS6300-50Q-EI-24X**（无 `a` 前缀） |
| 厂商 | **深圳市信锐网科技术有限公司（SUNDRAY）** |
| 产品线 | 安视交换机（RS 系列）→ RS6300 万兆盒式交换机 → 万兆汇聚型号 |

**关系说明**：信锐由深信服在 2014 年孵化成立，后独立运营。深信服自身**不生产企业级交换机**，其方案中的网络设备层（准入控制、端口级封堵、东西向流量阻断）依赖信锐交换机执行；渠道上"深信服交换机"是常见叫法。所以设备本身、配套文档、技术支持都在**信锐**这边，不在深信服官网。

对接深信服设备的联动能力是有的：RS6300 支持与深信服安全感知平台 SIP、防火墙 AF 做联动——交换机把流量镜像给 SIP 做分析，SIP 检测到失陷终端后下发封堵指令到交换机。

## 二、开放能力现状（这是重点）

### 2.1 设备侧（交换机本体）

官方规格书列出的网络管理能力只有三项：

- **SNMP v1 / v2c / v3**
- **WEB 网管**
- **SSH v2.0**（用于 CLI）

规格书中**完全没有出现** NETCONF、RESTCONF、RESTful API、Telemetry、OpenFlow 等任何字样。对比同档位的华为 CE 系列（RESTful + Telemetry + NETCONF 全套），差距是架构性的，不是配置开关问题。

**根因**：RS6300 采用「转控分离、瘦模式」SDN 架构——交换机是纯转发设备，配置下发和状态采集都由 **NAC 控制器**统一承担。厂商的设计意图就是让你不用碰设备本身，所以设备级的可编程接口没做。

### 2.2 控制器侧（NAC）

NAC 上的「开放接口」不等于通用编程接口，实际只有：

| 能力 | 说明 | 是否可用于自动化取数 |
|---|---|---|
| MQTT 开放接口服务 | **出站**连接，把 AP/NAC 数据同步给物联网平台 IPSIP，默认端口 1883。NAC/NMC 3.10.5 P1 起支线支持，3.11.0 正式合入 | 否，方向和数据范围都不可控 |
| 在线用户 / 无线状态 / 客流分析 3 个接口 | **3.10.0 版本才提供，且只有 3 个** | 极其有限 |
| 单点登录 | 生成免密跳转链接（MD5 签名），用于第三方系统跳转登录 | 否 |
| SNMP | 控制器级，v3 权限**只读**，认证算法仅 SHA/MD5，加密仅 DES | 可，但受限 |

> 注意：MQTT 那套是"我推给你"，不是"你来调我"，和 REST API 是两回事，很容易被误认为北向接口。

### 2.3 物联网平台侧（IOTP / IPSIP）

如果你需要的是**开放 API 文档**，信锐确实有一份完整的——但它属于**物联网平台**，不是交换机：
- 提供 access_token 鉴权、API Token 管理、IP 白名单
- 数据转发：平台以 POST 方式向第三方服务器推送设备数据和告警数据
- 单点登录、门禁授权、情景模式调用等

文档入口：物联网平台 → 平台管理 → 开放接口 → API 接口页面**可下载当前版本的 API 接口文档说明**。

结论：**物联网平台有 API，交换机没有。**

## 四、可行的自动化方案（既然没有 API）

### 方案 A：SNMP 采集（推荐）

**瘦模式下**：在 NAC 上「交换机管理中心 → 系统管理 → SNMP 配置」开启，**所有纳管的智能交换机统一开启，团体名一致**——这是瘦模式的优势，不用逐台配。

```
NAC 路径：应用中心 → 交换机管理中心 → 系统管理 → SNMP 配置
```

注意事项：
- 瘦模式下改配置要**先改交换机端、再改控制器端**
- 交换机管理 IP 用于 SNMP 服务器添加设备
- NAC 控制器自身的 SNMPv3 是只读的，认证算法只有 SHA/MD5，加密只有 DES——如果你的监控平台强制要求 AES，这里会卡住
- 若开启 SNMP 导致控制器 CPU 占用过高，需联系信锐用补丁包处理

**Python 取数示例**（需要 OID 表配合）：

```python
from pysnmp.hlapi import *

def snmp_get(ip, oid, community="sundray"):
    for errInd, errStat, errIdx, varBinds in getCmd(
        SnmpEngine(),
        CommunityData(community, mpModel=1),      # mpModel=1 → SNMPv2c
        UdpTransportTarget((ip, 161), timeout=2, retries=1),
        ContextData(),
        ObjectType(ObjectIdentity(oid)),
    ):
        if errInd:
            return f"请求错误: {errInd}"
        if errStat:
            return f"设备错误: {errStat}"
        return [(str(n), str(v)) for n, v in varBinds]

# 示例：取系统描述（1.3.6.1.2.1.1.1.0）
print(snmp_get("192.168.1.10", "1.3.6.1.2.1.1.1.0"))
```

### 方案 B：SSH 抓 CLI 输出

胖模式下可直接 SSH 登录，用 `netmiko` / `paramiko` 跑 `display` 类命令再正则解析。缺点是你已经在华为那边体会过的——**输出非结构化、格式随版本变、解析脆弱**。

### 方案 C：走控制器 Web 接口（不推荐）

NAC 的 Web 页面没有公开的、有文档保证的 JSON 接口。3.10.0 只放出了 3 个接口。不建议逆向，版本一升级就废。

## 五、如果确实需要 API，怎么办

以下路径按推荐度排序：

1. **联系信锐技术支持，直接问"RS6300 是否提供 NETCONF 或北向 REST API"**
   这类接口文档通常不在官网公开，需要签 NDA 或走项目渠道索取。售后服务热线 400-878-3389。
   问的时候带上型号 + 完整软件版本号（在 NAC 的交换机管理界面或设备 Web 页面查）。

2. **明确说出你的场景再问**——比如"我需要把交换机端口状态、CPU、内存、光模块信息定期采集进巡检报告系统"。厂商对有明确场景的需求响应完全不一样，会告诉你有没有可用接口，或者给你私有方案。

3. **确认你的诉求能不能从物联网平台满足**
   如果你要的是"取数据做看板/告警"，IOTP 的数据转发（POST 推送）+ 开放 API 可能就够了，不必卡在交换机本身。

4. **接受 SNMP 方案**
   对交换机巡检这个场景，SNMP 能覆盖端口 up/down、流量、错误包、CPU/内存、光模块光功率等主要指标，实际够用。真正缺的是"配置内容"层面的数据（比如当前 ACL 规则、VLAN 配置明细），这部分通常只能 CLI 抓取。
