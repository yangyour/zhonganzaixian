# 自动建单版本冲突事务修复

基线 main 5bbf945。静态复核发现两个 UPDATE 未检查受影响行数：自动建单尝试版本推进、事件与新工单关联。若 WHERE version 未命中，旧代码可能仍提交新工单及部分关联数据。

## 先复现，再修复

在自有全新 PG17.11 上，用真实事务和受控 JDBC 代理分别让上述 UPDATE 返回 0。旧代码两项测试均失败：未返回冲突，工单、历史、操作/outbox、事件/尝试、审计和幂等数据出现部分提交。证据保留于 attempt-before-fix；这是受控 CAS 未命中的复现，不是生产数据事故或声称实际并发已经触发过。

修复仅在两个更新点要求 affected rows == 1，否则抛出 409 VERSION_CONFLICT，使既有幂等事务整体回滚。没有捕获后吞掉冲突，没有自动升级版本，没有改动 V1–V45 SQL，也没有启动新的后台重试调度器。

## 新库复测

- 两项受控 CAS 回归均通过，10 张相关表的完整行指纹前后一致。
- 新增一项真实并行请求测试，运行 3 组“监控事件摄取触发的自动重试”与“人工补建”并行请求。每组只有一张持久工单，事件和尝试指向同一工单；请求只允许成功或明确 409，不留孤立记录。不等于穷尽所有并发交错。
- 四项既有事件中心 PG 回归通过，涵盖去重、长故障恢复、维护窗口与人工补建。合计 7 项真实 PG 测试，0 跳过。
- 新增前端组件回归：人工补建遇到 409 保留用户原因文本，不自动重试、升版本或刷新后假定成功。相关前端 90 项通过；本批不修改页面运行代码。
- API/数据库结构不变。自动建单耐久后台重试 Worker、配置发布、外部通知与完整 M5 验收仍是独立缺口，不能因为此修复标 DONE。

两次隔离库均已停止并删除临时数据及凭据，未访问原服务器、真实客户数据或外部渠道。默认构建与证据见 evidence/autoticket-cas-20261021/validation.json。
