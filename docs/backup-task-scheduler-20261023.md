# 原日志驱动的备份后处理调度

2026-10-23 第二个备份增量。连接本轮任务发现与既有归档、版本登记消费者；不重复实现 V48/V49 事务，不新增 SQL，不启用设备备份。

## 可执行代码与契约

`BackupTaskScheduler.assemble(...)` 接收显式 `BackupTaskSchedule`、指定 PostgreSQL 数据源、当前配置授权、原证明引用读取器、独立信封/对象/采集证据验证器及已有加密/存储适配器。公开装配入口为两个仓储和消费者每一步同时安装配置 grant 与数据库当前身份检查；绑定必须与 `backup-task-binding:<binding>` 完全相符。缺依赖不能装配，没有默认允许端口或自动 Spring Bean。

`BackupTaskSchedule.disabled()` 为关闭态，无查询、证明读取或写入。启用时必须明确 binding、1–100 个不同租户/设备目标、每页 1–50 项和 100–60000ms 的技术轮询间隔。这些是处理资源边界，不填入客户设备执行时间、业务重试次数、保留期限或删除政策。

`tick()` 每个目标处理一页；某设备查询失败不阻塞其他设备，同页失败任务不阻塞后续项。键集游标在扫描完成后回到起点；数据库日志始终保存待办事实，进程重启重新检查来源但不会生成新命令身份。`run(stopRequested, observer)` 提供显式轮询生命周期，轮次之间检查停止信号和线程中断；调用者拥有启动/停止，不自动启动服务。

返回 `Cycle(enabled, discovered, archiveRecorded, registrationsRecorded, reconciliationRequired, blocked, unavailable, discoveryFailures)`，只含数量，无私密错误或信封。`noProcessingErrors()` 仅表示本轮没有处理错误；禁用、未知结果、阻塞或依赖失败返回 false。即使没有任务，也不据此声称 KMS/OSS 就绪或当前备份健康。

## 原命令与恢复

1. `BackupTaskCommands` 用固定 v1 算法将 binding、原 actor、完整 scope、不可变 submissionId 与动作名称映射为稳定 UUID，不使用时间或随机值。权限版本刷新不改变原命令 ID，仍须通过当前授权。
2. 初始 STAGED/事件0 才能请求一次原归档 START；STORE_STARTED/VERIFY_REQUIRED 必须匹配同一稳定 dispatch，只核对原对象。人工 CONFIRM_NO_DISPATCH 后的 STAGED 和外部 dispatch 留作人工处理，不自动再次 PUT。
3. 独立证明来源按原来源读取真实、稳定的证明引用；引用自身不构成证明。来源未配置/不可用不调用消费者；对象、KMS/OSS、采集完成事实继续由已有独立验证器核实。
4. 每项每轮只调用一个消费者。归档成功后，下一轮重读 VERIFIED 终态再登记，不猜测版本。发现查询增加读取暂存版本关联的不可变运行租约；登记固定原 runVersion、原 lease 和已记录 archiveVersion，不偷偷改用新版本。
5. 消费者异常、丢回执、结果缺版本或结果不明计入 reconciliationRequired，本轮不重复执行。新实例构造同一原命令，依靠原日志幂等/CAS和回读恢复；租约到期不构成重传许可。
6. SQL 日志提供跨实例并发安全；进程内同步只保护游标。登记后 V49 记录使发现排除该项；已取得的陈旧页仍由消费者复核。调度器不执行设备命令、不重新加密、不释放设备租约或删除数据。

## 验证与部署边界
