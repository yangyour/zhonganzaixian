# 备份版本登记与运行完成的同事务关联

## 实现

新增PostgresBackupVersionRepository及显式V49，登记不可变版本元数据，并在同一数据库事务内追加对应V47运行成功事件。不修改已应用的V1–V48，不自动连接设备或供应商，不注册Spring Bean、API或Worker。

1. 先在当前授权、设备行锁和精确版本下核查V48原信封、终态VERIFY_OBJECT事件与原运行尝试/租约。
2. 关闭预检事务后调用强制注入的ObjectVerifier，实际复核原Scope、原编码字节数及原摘要对应的对象并认证。哈希引用本身不是证明；该步骤不能PUT、重加密或持有SQL事务。
3. 再使用既有PostgresBackupRunRepository.succeed开启完成事务，其当前授权回调重新核对范围、原信封、归档事件、运行版本及原租约；Authorizer必须核验当前身份并持有相关撤权锁至提交，不能只信前端权限快照。
4. 在运行仓储的CompletionVerifier回调中，由独立注入的CompletionPrerequisiteVerifier核查已完成采集及审批前提，再插入版本元数据。该回调只查询可信记录并持锁，不进行外部IO或设备动作。
5. 原运行仓储随后追加SUCCEED事件，一起提交。任一插入或验证失败都回滚。延迟外键与延迟完成约束阻止元数据单独提交，且绑定成功事件的版本、命令、原租约、执行证明引用和同一事务时间。

这是新版本登记工作流的原子性保证。既有底层运行仓储和历史合成测试仍可独立使用其受控完成验证器，不能声称所有历史SUCCEED都必须有V49登记；生产装配必须选择经过批准的完整工作流。

## 原对象、时间和回执边界

- 每个租户/版本、登记命令及运行尝试唯一，元数据只追加，不复制明文、原始密钥或第二份信封。
- 登记绑定加密对象摘要/大小、密钥引用、V48核验事件、独立对象复核引用和采集完成证明引用。只验证AES不能证明设备采集成功，空明文加密成功也不构成完成证明。
- object_observed_at取V48记录的“对象核验存在”观察时间，不伪造云对象创建时间。父运行StoredVersion.persistedAt承载同一个已知存在观察时间；registered_at由本次事务数据库时间产生，并与成功事件时间相等。
- 登记记录是当时的证据与事务事实；currentObjectHealthVerified、deviceExecutionAuthorized、retentionVerified、recoveryVerified均false，不作为未来对象可用性、保留、演练或执行授权。
- 不隐式释放设备租约，不将过期租约当成停止证明；完成保留原尝试租约绑定。真实停止/采集完成证据须由独立验证器确认。
- Q22失败计数口径及自动失败工单仍未确认/启用，没有编造连续失败策略。

## 幂等、未知结果与读取

相同原命令在当前授权下返回原登记及原成功版本，不重新核验对象、不PUT、不创建第二个版本。不同内容或不同命令不能替换已经登记的版本；新的合法操作者重放时仍保留最初登记人。

提交响应丢失不能判断事务失败。查询current和重放原命令核对原结果，不能重加密、换版本或盲重试。读取会验证元数据规范指纹、V48来源/核验绑定、前一RUNNING事件和完整运行快照中的StoredVersion，并确认租约事件未被替换；不会把数据库中的任意哈希字段直接当真实对象证明。

错误输出不带供应商异常、SQL细节、凭据或密钥。真实对象及执行证明实现必须显式注入，无默认放行实现。

- 已失败尝试不能借历史核验对象完成；受控破坏临时元数据指纹后读取拒绝，恢复后读回原记录。
