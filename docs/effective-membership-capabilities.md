# 当前成员有效能力在API的使用

## 发现及修正

角色值模型59ab506新增显式capabilities后，旧控制器仍多处调用Capabilities.forRole(member.role())，可能把受限集合重新扩张成基础类别的完整权限。纯测试先证明：38个控制器的55种读/写门禁在空集合下均错误放行；同55种完整历史授权路径正常。最初测试生成器对没有write参数的入口重复跑两次，152/76失败日志保留，不将重复项计作独立覆盖；去重后110项/55失败。会话新增6个场景也先失败。

40个控制器当前改用受信仓储返回的Membership.capabilities；不从前端请求接收成员权限。基础角色仍作为业务类别边界，不能靠能力字段越过内部/客户/仅平台管理员限制。配置修订读取单独要求configurations:read，创建/提交/审批/撤回要求configurations:write，原事务内再检查当前写能力；照片/报障已有回查点同样保留有效集合。

租户登记资源原来只有padmin类别检查，补明确能力tenants:read_inventory，仅在padmin类别声明中列出；不新增原先padmin没有的数据范围。当前成员须同时具有此能力与padmin类别，每目标租户既有padmin成员校验继续保留。代码能力目录同步新增这一操作，非正式客户权限矩阵或生产岗位批准。

会话、切租户及历史fixture投影不再补齐权限。已启用、受支持类别的空集合仍可读自己的会话和退出，但不会恢复业务能力；无效权限版本拒绝。未知类别/停用成员仍拒绝，原CSRF、幂等、版本、租户对象检查未删除。

## 实际契约及前端

API0.44.0路径和JSON字段形状不变。SessionResult新增两个x-mop语义说明：能力来自当前成员明确集合，合法成员可没有业务授权；租户登记资源路径增加明确能力元数据。未把identity_source改成项目本地认证。代码能力目录仍声明动态角色持久化未完成。

租户登记资源路由、双菜单和页面增加该能力检查；页面当前权限消失立即清理列表/详情，避免仅依据padmin类别继续显示。其他菜单的上层分组仍需针对独立能力组合继续检查，不能把这一批称为全部动态菜单验收。

## 验证与未完成部分

40控制器共58种独立门禁，各测试空授权拒绝与完整历史授权保留，共116项；另外4个实际控制器方法测试验证读取拒绝先于对象/照片/首页依赖调用，7个新增会话测试包括受限/空集合、每次回读、切租户、fixture投影、无效版本与空权限退出。均为隔离仓储/依赖，反射门禁测试不是HTTP过滤链验证。新增2项Vue/jsdom测试验证租户资源缺能力及撤销清屏；原一个前端源码断言依赖旧菜单字面量失败，更新为同时要求类别和能力，未放宽检查。

数据库尚未加载持久配置角色授权，历史五参Membership路径仍按原类别声明；本批没有创建角色/账户、迁移或切换服务器登录。因此这不是端到端动态角色上线。后续角色变更必须原子更新受影响成员permission_version，所有仓储与Worker事务、每目标租户查询均须复核有效授权，验证并发撤权、原请求重放、旧会话及后台作业。不会用前端菜单或本批API前置检查代替数据库授权。

实际数量与日志摘要见[证据](evidence/niko-effective-capabilities-20261005.json)。原服务器仍是固定部署基线225faeb，本批没有真实PG/HTTP/浏览器或新部署证据，正式合同NOT_RUN。
