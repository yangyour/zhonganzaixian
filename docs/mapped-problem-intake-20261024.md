# 映射来源问题到 raw、事件和工单的事务接线

2026-10-24，众安在线 MOP，M02/M01/M04 的一个已验证子功能。原有单次来源保存仅产生 V29 raw 或 V30 冲突隔离记录，事件中心没有消费该记录的调用方。本次增加显式问题消费入口：重新核验当前主机映射和来源，保存精确原文，再将 raw ID 写入事件成员，沿用现有归并、抑制和建单流程。整条写链使用原幂等事务；没有新增 SQL，V1–V55 字节不变。

## API 与运行配置

`POST /api/v1/monitoring-object-mappings/{id}/problem-intakes` 只接受 `expected_version`、`source_event_id`、`expected_source_definition_sha256`。请求须携带当前内部管理员会话、CSRF 请求头及 `Idempotency-Key`；不能提交租户、资产覆盖、事件原文、规则名、级别或恢复结论。

功能默认关闭。只有 `MOP_MONITORING_MAPPING_ENABLED`、`MOP_MONITORING_MAPPING_CAPTURE_ENABLED`、`MOP_MONITORING_MAPPING_PROBLEM_INTAKE_ENABLED` 三项都显式为 true 才允许新消费。还须有有效映射策略、来源定义/秘密引用、归属标签、资产版本和未过期的发布证明；没有给客户配置任何默认业务值。资产映射读取增加 `problem_intake_enabled`，页面据此展示操作。开发示例见 `deploy/examples/monitoring/problem-intake-settings.json`，示例全部关闭，不会自动加载或启用。

事务顺序如下：

1. 复核当前成员能力，直接取得映射根行的写锁，避免授权共享锁升级造成并发死锁；重核版本、资产、策略、复核人及证明时效。
2. 从已配置来源读取归属和指定事件，验证唯一主机、池、租户、资产及来源定义。外部读取结束后再次复核本地授权和配置。
3. 以 `synchronous_commit=on` 保存原始秒/纳秒及精确字节。来源键相同、内容不同只保存冲突候选，回执 `business_processed=false`，不推进业务事件。
4. 校验服务器读取的严格 JSON 信封。只接受 PROBLEM，拒绝未分类级别 0、来源时间晚于接收时间、错主机/时间/键、重复 JSON 键、额外字段和尾随正文。规则身份由 pool UUID 和 trigger ID 确定，严重级别沿用 Zabbix 已命名的五级；不替代 Q14 的正式优先级批准。
5. 在同一事务写入业务事件、带 `raw_event_id` 的成员、既有建单/工作流效果和审计。业务摘要显式取毫秒，raw 保留纳秒。相同来源重放保留原 raw、事件、工单与首次回执；旧事件成员若没有同一 raw 引用，返回 409，不修写历史。

回执包含 `record_id`、`raw_outcome`、`event_id`、`event_version`、`ticket_id` 和来源归属核验依据。冲突时 `record_id` 指隔离候选，事件/工单均 null。回执仅说明原事务结果，`recovery_confirmed=false`、`dispatch_allowed=false`；raw 表原有 `UNVERIFIED/STORED_ONLY` 字段保持不变，不把归属匹配描述为设备签名认证。

原 `/captures` 行为保持为 raw 保存，页面另有“读取问题并关联业务事件”。请求结果不明时保存原请求键与正文；后续读取失败仍保留已提交回执和事件入口，权限或身份变化清除该内容。新增事件链接有下划线，键盘和桌面无障碍检查通过。原始恢复信号继续走当前周期观察证据流程，本入口不确认 t2。

## 实际验证与失败记录

最终验证复用指定 LAN 的 PostgreSQL **17.9 / 活动 V55**，使用新建、明确标记的两个 SYNTHETIC 租户、无登录凭据主体和测试资产。**来源协议是隔离合成输入；PG 仓储、事务、权限和并发是真实执行。** 这不是实际设备来源消费或供应商外发验收。

- 6 项真实 PG 场景全部执行，0 失败/错误/跳过：raw→成员→事件→工单、换键/新装配重放、六路并发、冲突耐久隔离、提交前回滚后恢复、恢复/未知级别/旧版本/跨租户拒绝。
- 六路并发有 4 次有界锁等待超时，测试只允许 SQLSTATE 57014 进入受控恢复，并使用各自原路由/原键/原体顺序重试；最终仅一份 raw、成员和工单。没有盲重试来源或把失败记成成功。
- 非本轮命名空间行摘要及活动迁移历史保持，所有原记录保留。新主体与成员已停用，自有连接关闭、环境锁释放；0 迁移、建库、删库、设备联系、外发和部署。
- 本地受影响 Java 191 项定向通过，后续新增边界及格式复验另 23 项通过；Web 114 项通过；Node 契约 215 项与生成一致性通过；类型检查、生产构建和静态策略检查通过。
- 实际 Edge 3 场景通过：1024px 的键盘消费/回执保留/权限撤销、1440px 的原请求键恢复、未配置门禁。零整页横向溢出；1024px axe 检查零问题。浏览器 API 为显式合成拦截，不能计作真实 HTTP 到监控源的完整验收。

前几轮失败均保留在 [证据目录](evidence/mapped-problem-intake-20261024/validation.json)：首轮测试种子遗漏站点，次轮误让运行账号读取 Flyway 历史，之后严格 raw 守卫拒绝保留 V55 验证库。只读比较发现，该库 schema 克隆后的 CHECK 表达式摘要与活动库不同，且 Unicode 换行字面量已变化；克隆器的 `splitlines()` 会拆分这些 SQL 字面量，SQL 重解析还会规范化部分表达式。没有放宽守卫、修改冻结迁移、修写既有库或授予运行账号额外权限。最终以显式 `--scope active-isolated-tenants` 在活动库的新隔离命名空间验证，没有自动环境回退。另一次因其他设备流程持有共享锁而未开始连接或写入。

可复验命令：`py -3 -X utf8 tools/verify-mapped-problem-intake.py --output .local/<新的目录> --scope active-isolated-tenants`。工具先原子取得环境锁，读取私有配置并验证固定主机与项目，严格核对 V55 历史，准备新隔离主体；不会执行迁移、修复库或接触真实设备。默认 retained 模式仍会保留并暴露原库的严格守卫失败，不会静默换环境。
