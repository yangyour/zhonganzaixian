## 二、链路设计

```plain text
计划发布（草稿 → 审核 → 运行配置发布）
  → backup-worker 按 daily_local_time 生成运行（PG 租约，按设备互斥）
  → 读取凭据引用（凭据库，明文不出服务端）→ SSH 只读执行 backup.commands（按设备类型）
  → 规范化（去时间戳 / 计数器等噪声行，规则 = backup.noise_filter）
  → AES-256 加密写 MinIO，PG 记录版本元数据（sha256、字节数、密钥版本）
  → 与上一版本做脱敏 diff（RedactedBackupDiff）→ 有变更则生成 info 事件（D15）→ 变更报备匹配（D10 / M6-7）
  → 失败：按 retry_count / retry_interval_min 重试；连续失败达 failure_ticket_count → 自动 P3 工单（source=backup_failure）
```

## 四、后端实现

- 依赖：新增 SSH 客户端库（需走 `doc/development/05` 成熟组件选型与许可评审，如 Apache MINA SSHD / sshj），只允许执行配置中的只读命令，校验 host key。
- 领域：`BackupScheduler`（计算下次执行）、`ConfigNormalizer`、`BackupFailureStreak`（连续失败语义由 Q22 配置）；`BackupRunState` 改为注入配置值。
- backup-worker：独立进程，参照现有 Worker 的 PG 租约模式；同设备互斥；结果未知时不盲目重试。
- API（202 + `operation_id`，前端显示「同步中」直至回读确认）：
	- `POST /api/v1/backup-plans`（由草稿发布）、`POST /api/v1/backup-plans/{id}/run-now`
	- `GET /api/v1/backups?asset_id=&from=&to=&result=`（设备、时间、结果、大小、差异行数、耗时）
	- `GET /api/v1/backups/{versionId}/diff?against=`（左右分栏 diff，仅 MSP / 平台角色）
	- `POST /api/v1/backups/{versionId}/download`（重新授权 + 审计 + 900 秒签名地址，客户角色 403）
	- `POST /api/v1/backups/{versionId}/baseline`
	- `GET|POST /api/v1/recovery-drills`
	- `GET /api/v1/customer/backup-overview`（客户只读：设备 + 最近备份时间 + 是否正常）
- 自动建单：复用 D15 / M5-4 的建单规则与幂等键（tenant + incident）。

## 五、前端实现（apps/web）

- `BackupsPage.vue`：结果列表（筛选设备 / 时间 / 结果）+ diff 视图 + 版本历史（按日期检索、标记基线、受控下载）。
- `RecoveryDrillsPage.vue`：「距上次演练天数」列，超过阈值标红；无「自动恢复」入口。
- 客户视图：设备列表仅显示「最近备份时间」「备份是否正常」，无下载按钮和 diff 入口。
- 明确不提供「自动回滚」按钮（M6-3）。
