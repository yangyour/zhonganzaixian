# 已发布配置驱动的工单开单（2026-10-20）

## 接线

POST `/api/v1/tickets/{ticketId}/lifecycle` 接收精确两字段：`expected_version: 0` 和内部工程师明确选择的 `priority: P1/P2/P3`。不得根据报障紧急程度自行映射优先级。请求遵循当前权限、CSRF、幂等和工单关系检查，存在生命周期则冲突。

服务端在同一幂等数据库事务中锁定工单，读取数据库毫秒时刻及当前租户的 V32 生效发布。未生效、已禁用、过期、缺失或类型不正确均返回 `CONFIG_PENDING`，details 包含配置键和原因，不回退到登记中的可配置默认值。固定约束只读取既有登记且核对20字、72小时、2次，不可被发布覆盖。

开单原子保存状态、时间、预算、实际采用的配置输入及发布引用、快照摘要、审计和幂等结果。不会运行迁移、创建凭据、自动授予角色、发送通知或修改客户批准状态。

## 配置结构

缺失项清单：`deploy/examples/ticket-lifecycle-configuration.json`。仅示例形状，全部未知业务值为 null，不直接发布、不含秘密。现有配置提案、审批及发布流程保持不变。

- `tenant.plan`：`基础/标准/进阶`，亦接受对应 `BASIC/STANDARD/ADVANCED` 规范代码。
- 各档响应、P1/P2恢复、客户确认小时：对象，以中文档位为键，值为正数。确认小时必须正整数；分钟换算必须为精确正毫秒。
- `sla.advanced_p3_recover_min`：明确发布的正分钟数。
- `sla.tenant_work_calendar`：精确包含 `timezone: Asia/Shanghai`、UTC毫秒 `coverage_start/coverage_end`、`complete: true` 和 `working_windows: [{start,end}]`。最多1000段，不生成工作日默认时间。基础档必须有覆盖足够的完整日历。
- `sla.basic_standard_p3_next_day`：精确包含 `kind: CALENDAR_DAY 或 WORKING_DAY`、`cutoff: HH:mm`、`timezone: Asia/Shanghai`。次工作日还需完整日历，只有整日覆盖已知时才能跳过空白日；技术搜索上限3660日。没有Q08规则不补“次日18点”等默认值。

## 前端与未完成项

详情未开单时，仅授权内部用户可明确选择优先级并勾选核对后创建。未知结果仍使用原动作、正文和幂等键重试；客户不可开单或覆盖档位、日历与截止时间。

补充回归纠正了前端重开成功回执的状态判断：客户重开进入 IN_PROGRESS，仍未解决进入 REOPENED，与既有领域规则一致。

这是测试运行发布的业务消费者，不是客户生产批准。通知/自动关闭/升级 Worker、实时暂停恢复和正式SLA考核仍待后续接线；历史原始截止时间不会被转派重置。
