## 接口客户端

新增 `WeComClient` 和 `WeComCredentials`，提供应用读取、成员校验、文本消息接口与网页授权码换成员身份。接口固定为企业微信官方 HTTPS 源，保留证书校验，禁止重定向，限制响应大小；错误仅输出分类与供应商错误码，不回显密钥、access_token、原始响应或含密请求地址。

应用凭证按接口返回的 `expires_in` 缓存并提前刷新，同进程并发刷新串行化。仅明确的 token 失效响应允许刷新后重试一次；消息发送超时、网络断开或无法确认响应时保留 UNKNOWN，不自动重复发送。接口 errcode=0 记录为 ACCEPTED，不代表用户已收到或已读。

## 消息发送与账号绑定

V38新增项目内 `mop_wecom_binding`、`mop_wecom_delivery` 和 `mop_wecom_login_state`。绑定和业务写入复用当前租户授权、CSRF、幂等收据、乐观锁及审计；管理其他用户的绑定需覆盖该账号全部既有管理范围。UserID不用于猜测或自动创建平台身份。停用绑定推进认证版本，使既有会话失效。

消息先以202耐久入队，Worker提交PROCESSING后才调用企业微信。每条记录只有一次外部发送尝试；进程中断或响应不明确时记UNKNOWN，不重领重发。发送前重新核对成员、权限版本及绑定。本人站内通知可通过显式操作发给本人绑定的成员，来源通知与绑定组合永久去重，不能修改接收人或发送其他人的通知。管理页显示当前配置企业和应用的记录，隔离其他合成测试应用的记录。

## 企业微信登录

新增网页扫码及企微内授权入口，登录回调只允许服务端固定域名。每次发起生成互相独立的随机state和浏览器关联Cookie，数据库仅保存二者摘要，5分钟内一次性消费。关联Cookie为HttpOnly、SameSite=Lax；原项目会话Cookie继续使用Strict。发起页面与回调必须同源，避免本机地址发起却回到公网域名导致浏览器关联丢失。

回调通过官方接口换取企业成员并核验激活状态，随后只使用既有显式绑定和平台当前认证版本建立会话。跨租户或未绑定成员不能登录，停用用户或撤销会话后的权限不会保留；前端导航、页面恢复和权限刷新均识别 `wecom` 会话来源。成功与拒绝均记录脱敏审计；无效回调不注销另一个既有有效会话。

已真实打开企业微信官方二维码页，并显示正确应用名“MOP运维服务门户”。用户曾要求重新生成二维码，随后明确“这个跳过，后续再测”。因此真实扫码回调保留待验，不把二维码显示或隔离测试记为真实登录成功。

## 本地运行与复现

本机开发入口为Vite的127.0.0.1:80，API为127.0.0.1:18038，SSH CONNECT代理为127.0.0.1:18889，指定LAN数据库转发为127.0.0.1:15438。`tools/run-wecom-dev.py`读取既有LAN私有配置，使用受限数据库账号，不执行迁移或创建基础组件；`--dispatch`与`--login`分别显式开启发送和登录。应用私有归档里的状态字段不是运行开关。

```powershell
# 使用现有项目工具链构建classes和本机.local/api-classpath.txt后，在独立终端运行：
py -3 tools/wecom-dev-tunnel.py
py -3 tools/run-wecom-dev.py --dispatch --login

# 在apps/web目录运行前端：
$env:MOP_API_PROXY_TARGET = 'http://127.0.0.1:18038'
$env:__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS = 'mop.all-online.com.cn'
npm.cmd run dev -- --host 127.0.0.1 --port 80 --strictPort

# 在项目根目录打开隔离的本地登录浏览器：
node tools/open-wecom-dev-browser.mjs
```

隔离浏览器仅在自身进程中把业务域名解析到本机，未修改系统hosts、公共DNS或已发布站点。普通浏览器访问公网域名仍进入原站点。当前HTTP只用于明确的本地测试配置，公网HTTPS证书问题仍独立保留。已发布服务器应用没有随本轮切换。
